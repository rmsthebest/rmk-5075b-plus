# sim-rs: our own Akko 5075B Plus simulator

A Cortex-M3 interpreter and WB32FQ95 models in Rust, with the tests as plain
`cargo test`. It is the gate for every firmware image: the workbench's "Run
sim tests" (`../tools/bench.py`) runs the whole suite, about 100 s, and
freezes the akko-rmk it ran. The Renode sim in `../sim` runs the same suites
as a cross-check ("Cross-check in Renode"). The QMK build runs here too
(`qmk_reference.rs`, `qmk_power.rs`).

```fish
sim-rs/run.sh                   # build and snapshot the images, run every test
sim-rs/run.sh -p wb32-sim       # cargo test arguments pass through
cd sim-rs; cargo test           # against the last snapshot
```

## Debugging an image

`akko-sim gdb <image> [port]` boots an image halted at its reset vector and
serves GDB on localhost, as a debug probe would on the keyboard:

```fish
cd sim-rs; cargo run --release --bin akko-sim -- gdb akko-rmk 3333
gdb target/images/akko-rmk -ex 'target remote :3333'
```

Breakpoints, `stepi`/`step`, Ctrl-C, registers (the core's, `xpsr`, `msp`,
`psp`, `primask`, `basepri`, `faultmask`, `control`), memory (flash writes go
straight in, as `load` does) and a BKPT halting the core. `monitor reset` is a
system reset (SRAM kept), `monitor time` the emulated time, and `monitor key
<row> <col> down|up` presses a key. Emulated time stands still while halted and
runs as fast as it can otherwise, with the USB host and the board's parts going
on as in the tests. No watchpoints yet.

`run.sh` builds the firmware in `target/sim-rs*` (not the repo's `target/`, so a
Renode run can go on at the same time) and copies the images to
`sim-rs/target/images/`, which is all the tests read. `AKKO_SIM_IMAGES=` points
them at another directory.

## Crates

| Crate | What |
|---|---|
| `cortex-m3-emu` | The core: Thumb-2 interpreter, NVIC, SysTick, SCB, DWT. Knows nothing about the chip. |
| `wb32-sim` | The WB32FQ95: memory map, image loading, peripheral models. |
| `akko-sim` | The board (ROM stub, key matrix, radio, LEDs, SPI flash, USB host) and the test harness. |

## References

The simulator checks our PAC, HAL and firmware, so it must not be built from
them. Its references are the Renode sim (its models were checked against the
QMK binary and its golden traces) and the keyboard itself:
- No crate here depends on `wb32-pac`, `wb32-hal` or any other crate of the repo's; `crates/akko-sim/tests/deps.rs` checks `Cargo.lock`.
- Register facts come from `../sim/peripherals/*.py`, the vendor `wb32fq95xx.h` and the reference manual (RM2905025), and each model says which.
- Where the board and a model disagree, the board wins, recorded in [BOARD_FACTS.md](BOARD_FACTS.md).

## Status

- Step 1: the workspace, the memory map (flash at 0 and 0x0800_0000, ROM, SRAM), ELF and binary loading, the ROM stub. Accesses to nothing, and stores to flash or ROM, are recorded as `Diag`s rather than faulting, as Renode logs them.
- Step 2: the core. The decoder agrees with llvm-objdump on every instruction of the images, the ROM and a random blob (`tests/decode_oracle.rs`); the interpreter, exceptions, NVIC, SysTick, SCB and DWT have their own tests (`cortex-m3-emu/tests/cpu.rs`). Timing is Renode's: 100 MIPS, SysTick and CYCCNT at 96 MHz. A sleeping core jumps to the next event.

- Step 3: the core against Renode. `compare/renode-compare.sh <image> [secs]` records Renode's run (every instruction, every peripheral access) and steps our core through it in lockstep: peripheral reads get Renode's values, writes must match, interrupts are taken where Renode took them, and reads of the core's timers take their registers from snapshots Renode logs (`compare-renode` finds the PCs and asks for another run). It stops at the first difference. Every image matches: m1a, m1b and m3 (9.8M instructions, 0.1 s), m2 (0.5 s), akko-rmk and its mac build (11M instructions, 51k accesses, 0.3 s), and the ROM's boot from the dump (5M instructions, 454k accesses, 0.05 s). Our SysTick was pending at 51 of the 52 SysTick interrupts Renode took in akko-rmk; the other interrupts wait for the peripheral models.

- Step 4: the system controller (PWR, ANCTL with the ANAKEY lock, IWDG, RCC), the cache controller, GPIO with AFIO and EXTI and the key matrix, ported from the Renode models, and TIM2 written fresh to the board facts. `boot_guard.rs` and `m2_hal.rs` are the Renode suites ported test for test, and pass. `akko-sim trace <image> [secs] [regex]` prints the register writes as `../sim/trace.sh` does; `compare/trace-diff.sh` diffs the two. m1b and m2 match line for line over 0.5 s; m3 and akko-rmk match until their first access to a peripheral not modelled yet (USB, QSPI). Seeded model bugs (no EXTI falling edges, the PLL never ready) fail the ported tests.

- Step 5: the USB device controller (MUSB, with CRC/SFM), the scripted host (usb.py's host, with usb_rom.py's bulk pipe folded in; its transfers are async functions stepped every 100 us, as usb.py's generators), and the ROM sim's FMC and SYS. `m3_usb.rs` (15 tests, 1.2 s), `rom_sim.rs` (enumerate, download and leave: 9 tests on both the ROM dump and rom/rust's build) and `rom_traces.rs` (the `boot`, `download` and `leave` write traces in `../rom/sim/traces` match line for line, on both) pass. Two adjustments to Renode's traces, both in `rom_traces.rs`: its log folds a run of identical lines into two, and its AIRCR reads with reserved bit 13 set. m3's register-write trace matches `sim/trace.sh` over 0.5 s. Seeded bugs (a stuck host data toggle, the wrong USBPRE) fail the m3 tests. peek.robot comes with the SPI flash in step 6.

- Step 6a: the DesignWare SSI (QSPI and SPIM2 share it) and the 16550 UART3 in wb32-sim; the board's NOR flash (C12 chip select, kept across resets), WS2812 chain and radio module in akko-sim, as `SsiDevice`/`UartPeer`s ported from qspi.py, spim2.py and uart3.py. The host's log now runs on across a system reset, as Renode's does. `m4_rmk.rs` (29 tests, 17 s) and `peek.rs` (rom/sim's peek.robot, on akko-rmk built with `rom-peek`) pass. akko-rmk's register-write trace, flash commands included, matches `sim/trace.sh` over 8 s (7,005 writes). A seeded NOR bug (programming that doesn't clear bits) fails the five storage tests.

- Step 6b: `m5_lighting.rs`, all 29 tests of m5_lighting.robot (11 s), with leds.py's colour maths and layout reading in `tests/common`, which m4 now shares. A seeded decoder bug (RGB for GRB) fails the 13 colour tests; a radio reporting the battery 1% high fails the two that read the level.

- Step 6c: `m6_wireless.rs`, all 28 tests of m6_wireless.robot (18 s), stop mode included. Stop mode is modelled as in Renode: SysTick off, SLEEPDEEP and a WFI that any interrupt ends; what a stop does to the clocks on the chip (BOARD_FACTS.md) isn't modelled yet in either sim. A seeded UART bug (LSR never shows a byte) fails all 28. The whole suite (186 tests) takes about 100 s.

- Step 7: `m7_power.rs`, all 5 tests of m7_power.robot (3.7 s; Renode takes minutes), with the handler counts as a PC-hit counter in the chip (`Wb32::pc_hits`, Renode's `cpu AddHook`s). On the same image Renode and ours agree within a frame: lights on 5.91 M vs 6.00 M insns/s (one more 16 ms frame in our second), off 0.21 M vs 0.22 M, asleep 0.07 M both, key held 33.43 M vs 33.37 M, wakes within 1/s. Their timing drifts apart from SysTick's enable on, and it is Renode's SysTick that's off: it breaks ARM DDI 0403E B3.3 in three ways (BOARD_FACTS.md, pinned by `cpu.rs` `systick_*`), found by running the same probes from SRAM in both and logging the firmware's own CVR reads. Renode's default mode also counts instructions in translation blocks (96,555 in the first millisecond against 96,186 with `cpu MaximumBlockSize 1`, which matches ours exactly). With spec timing, one m7 press lands on a WS2812 frame and waits 9 steps for it, so the press bound is now 10 in both suites.

- Step 8: the switch-over. sim-rs is the workbench's gate; there's no test selection or smaller gate any more, as the whole suite takes about 100 s (2 min with the image builds). `run.sh` runs with `--no-fail-fast`. `sim/affected.py` is gone; Renode's `sim/run.sh` stays for the cross-check.

- Step 9: the QMK binary. `run.sh` snapshots `../qmk_5075b_plus/.build/akko_5075b_plus_via.elf` (or `$QMK_ELF`) as `qmk-via` after checking that its flash bytes are `akko_5075b_plus_fixes.bin`'s. `qmk_reference.rs` (all 8 tests of qmk_reference.robot, 7 s) and `qmk_power.rs` (compare/qmk_power.robot's 3 cases, 9 s against Renode's 25 min each) pass. The core can stub a function (`Cpu::stubs`: set r0, return), as Renode's `cpu AddHook` does with `spi_flash_start`. Two golden traces end where Renode goes wrong, not QMK: in SysTick nested over the QSPI interrupt, Renode's ICSR reads RETTOBASE, so ChibiOS's interrupt epilogue leaks a frame on the idle thread's stack per nested tick, until the stack overwrites `spiStarted` and `spi_stop` leaves the flash selected (BOARD_FACTS.md; found by watching the variable in a lockstep `compare-renode qmk-via`, pinned by `cpu.rs` `rettobase_is_clear_in_a_nested_handler`). The tests hold ours to the goldens up to that point, then to what the spec gives: CS high after a 2048-byte READ, and QMK going on to USB. QMK runs at the CPU's 100 M instructions/s, never sleeping, in both sims. The suite is 198 tests, about 2 min with the builds (205 with step 9b).

- Step 9b: the GDB stub (`akko_sim::gdb`, `akko-sim gdb`). The core stops before a breakpoint's instruction (`Cpu::run_until_break`, resuming from one) and, with a debugger attached, a BKPT halts it instead of escalating to HardFault (ARM DDI 0403E C1.6.1). `tests/gdb.rs` checks the packets, Ctrl-C over a socket, and a session with GDB itself (`gdb`, or `$GDB`): break at main, continue, stepi, memory, a register write, `monitor time`, detach.

- Hardware gaps, step 1 (board wiring; plan in memory `sim-hw-gaps-plan`): the board's parts drive the chip's pins (`akko_sim::parts`): the knob as a quadrature encoder with detents (`Board::knob_edge`, bounce in `T::knob_step_bouncing`), the Win/Mac switch, and the charger (A15 low while charging, its level the radio's battery). `Board::plug` puts the cable in and takes it out: A7 follows VBUS, and the host sees a cable out as an idle bus (a suspend). B1 high cuts D+'s pull-up, so in wireless mode the host loses the device (a bus reset on the device's side), and USB Vial can't be reached there: m6 reads Vial through the dongle (AF 60/61). A8 low powers the LEDs down (dark, no data). The WS2812 chain, the NOR flash and the radio check their pins' alternate functions. The board starts with the cable in and the battery full, so tests on the battery unplug first (the firmware doesn't stop with the cable in, and charging hides the low-battery flash). BOARD_FACTS.md has the wiring; `tests/board_wiring.rs` the new checks.

- Hardware gaps, step 2 (the radio module): `radio.rs` is a behavioural model of the module, from module.h's command tables: the selected device, a bond per device, the link (none, pairing, connected, disconnected, rejected). A select of a bonded device connects after `connect_ms` (an unbonded one stays down); A6 52 clears a bond; A6 51 pairs (5B 31, then accepted, rejected or timed out per `pair_outcome`) and must follow the device's set-up (A9 for BT, AD for the dongle); A6 53/70 are answered with the charger's level and the version; the charge state and the 30 min sleep settings are kept. Tests drive the far side: `Board::host_present`, `link_drop` (back after a while, or not), `dongle_host` (60 00/01), `vial_via_dongle` (AF 60/61). Faults (bad sum, lost byte, bit error) spoil the module's next frames, and `retransmit_ms` sends unACKed ones again. A report while the link is down is an error. The module keeps its state over a keyboard reset (it's its own chip), and selecting the connected device again re-announces CONNECTED. The old `flags` (uart3.py's register) are named fields now. m6 uses the model instead of hand-sent state frames, except a host resume while the module has no link, which only the firmware's side can show. Found: the firmware selects again on a key while the link is down, at most every 500 ms, not by itself. The module's timings are assumptions (BOARD_FACTS.md, open questions); the keyboard's queue being idle before battery and charge frames can't be seen from the module and isn't checked.

- Hardware gaps, step 3a (the clock tree, in `wb32-sim` `sysctl.rs`): the RM's reset values (Renode's RCC were 0), ANAKEY reading 0, ready flags that rise after the DS start-up times (the HSE crystal's 2 ms assumed), MAINCLK switching on MAINCLKUEN only to a stable source (else `Diag::ClockNotReady`), and `Sysctl::clocks()`: MAINCLK, HCLK, PCLK1/2 and the USB clock from the registers. The board's crystal is 12 MHz (QMK's mcuconf), so the firmware and QMK run at 96 MHz; the ROM at 48 MHz with APB2 off. The USB host checks the USB clock is 48 MHz instead of USBPRE's value (no more ROM special case). A system reset keeps PWR SR1, GPREG and CFGR. The Renode goldens are compared with AHBENR1's reset bits or-ed in (`common::golden`, `rom_traces.rs`). Nothing runs from these clocks yet: the core is still at Renode's 100 MIPS (step 3b). Seen: start-up now waits ~2.2 ms for HSE and the PLL, and m3's 30 s DFU timeout starts after USB's 50 ms blocking D+ delay, ~100 ms at the current core rate.
- Hardware gaps, step 3b (the core timed from HCLK): `Bus::hclk_hz` gives the core its clock (`Wb32` reads `Sysctl::clocks()`, cached on every RCC/ANCTL write); an instruction is one HCLK cycle (TRM costs are step 4), so code before `rcc::init` runs at MHSI's 8 MHz. SysTick counts HCLK, or HCLK/8 with CLKSOURCE 0, and a clock switch rebases SysTick and CYCCNT (`Ppb::set_hclk`). `Config` keeps only `prio_mask`. Moved: m1b's `asm::delay`-timed blinks (8 MHz before its clocks: 1 s per `delay(4M)` here, 1.5 s on the board), QMK's busy loop at 96 M instructions/s (`qmk_power.rs`), the ROM's 1.5 s start-up disconnect at 48 MHz (`rom_traces.rs` runs 1.78 s), and m7's latencies (press 5 steps, release worst 56); m7 and qmk_power now keep their own bounds, the robot copies Renode's.
- Hardware gaps, step 3c (clock gating and RCC resets): a peripheral answers only while RCC clocks it (`Sysctl::clock_on`: its enable bit, the APB bus clock and BMXnEN, its reset bit clear); otherwise reads give 0, writes are dropped and `Diag::ClockOff` reports it, which `Board::errors` counts (with `ClockNotReady`). Setting a reset bit resets that model (`Gpio::reset_port`/`reset_afio`/`reset_exti`, `Musb::reset` keeping the host's side, TIM2, the SSIs, UART3, FMC, the cache). TIM2 counts PCLK1 (`Tim2::set_clock`; 0 while gated) instead of a fixed 96 MHz. The system control block and the sim's GPIOD control words have no gate. No image touched a gated peripheral.
- Hardware gaps, step 4 (cycle costs, `cortex-m3-emu` `timing.rs`): each instruction takes its cycles from the Cortex-M3 TRM r2p0 (ARM DDI 0337G Table 18-1 and 18.3, zero wait states): loads 2 (1 when pipelined after a load), stores with an immediate offset 1, LDM/STM 1+N, LDRD/STRD 3, MLA 2, long multiplies 3-7 and divides 2-12 by operand size, unaligned accesses +1/+2, a taken branch's refill 1 (immediate), 2 (register) or 3 (loaded PC), one more to a 32-bit instruction at a halfword, TBB/TBH 6; exception entry 12, tail-chain 6, return 10. The board's 3-cycle delay round comes out of the table, so no wait states. `Cpu::cycles` counts clocks awake. Moved: m1b's blink is 1.5 s and it's back in DFU at 90 s, as on the board; USB's 50 ms D+ wait (`asm::delay`) is 150 ms, attaching at ~158 ms (m3 windows 0.4 s); m7 press 6-7 steps, 17 on a WS2812 frame send, release worst 63 (bounds 18, 66; awake 8.7 M cycles/s lights on, 0.39 M off, 50.4 M key held); QMK runs ~60 M instructions in its 96 M cycles a second (`qmk_power` checks cycles now). The root README's table uses the measured cycles instead of an assumed CPI 1.25.
- Hardware gaps, step 5a (SSI timing, `wb32-sim` `ssi.rs`): frames shift in (DFS + 1) × SCKDV bus clocks while enabled with SER set, from a TX FIFO into an RX FIFO (none in TMOD 01), with BUSY, TXFLR/RXFLR, TXO/RXU/RXO and the RM's reset values (CR0 0x0100_0007, IER 0x1F); SPIM2 is 4 deep (RM 22.2), QSPI stays 8 (the RM contradicts itself). The SSIs keep time like TIM2 (`Wb32::clock_timers`, `next_event`), and `SsiLine` gives a device the SCLK rate and each frame's end. The WS2812 decoder times the 280 us latch on the wire, idle line included, and checks SCLK = 3 MHz rather than BAUDR. Found: at 4 deep, the HAL's QMK-style WS2812 feed (send and receive, FIFO half full) took an interrupt about every byte, ~250 cycles of a byte's 256, so the CPU was nearly all in it for each 3.7 ms frame: lights-on idle 24.7 M cycles/s, a press up to 4 ms, a fast knob spin through the dongle lost a step (a sampling profile, PC every 1 us, found it). The HAL now feeds transmit-only with TXFTLR at a quarter of the FIFO (an interrupt per 3 bytes): lights on 10.2 M cycles/s, press 9 steps worst, every knob step kept. The QMK goldens were recorded at Renode's 8-deep FIFO and IER reset 0: `common::at_fifo_depth` rewrites the depth probe, `fold_repeats` folds the extra IER write, and m5 names where our SPIM2 sequence leaves QMK's.

- Hardware gaps, step 5b (UART timing, `wb32-sim` `uart.rs`): UART3 shifts each character out and in at its line rate (16 × PCLK2 / (DLH:DLL + DLF/16) a bit: 86.8 us for QMK's 8N1), through 16-deep TX and RX FIFOs (1 with the FIFOs off), on PCLK2 (`Wb32::clock_timers`; 0 while gated or stopped). The peer gets a byte when its stop bit ends; what it sends goes onto `Uart::wire` and arrives one character at a time from when the line is free. A full RX FIFO overruns (LSR.OE, the line-status interrupt first), a byte arriving without a clock is lost (`Uart::lost`), and a THR write to a full FIFO is an error that `Board::errors` counts. IIR follows the RM's priorities, with the character timeout timed and THRE's raise/clear on transitions. The chip drives the board's RX pin (C11, `Uart::rx_pin`) bit by bit, so EXTI 11 sees the start bit. Not modelled: PTIME, parity and framing errors, break, DMA. All the radio tests pass at the real character times.

- Hardware gaps, step 5c (flash busy times): the NOR holds WIP for its typical program and erase times (PP 1.4 ms, SE 60 ms, BE 0.7 s, `nor::busy_ticks`) instead of two status reads, and the FMC's CON bit 7 reads busy for the datasheet's tPROG 2.1 ms, tERASE 6.4 ms, tME 25.6 ms (`fmc::op_ticks`). A fetch or read of flash or the ROM during an FMC op is `Diag::FlashBusy`, which `Board::errors` counts; the ROM's SRAM poll routine keeps it clean. Found: EE_CLR's release, if it came while the hold's lighting save was still erasing, was dropped by the action hook, so RMK never cleared its storage or rebooted. The firmware now always keeps EE_CLR from RMK and handles the release in the lighting task after its save, calling `rmk::storage::reset` (made public in our rmk fork). m5's EE_CLR test releases inside the erase.

- Hardware gaps, step 6 (stop mode, `Wb32` `Bus::sleep`/`woke`): a WFI or WFE with SLEEPDEEP and PWR CR0 PDDS 00 stops the chip, unless an EXTI request is pending (then `Bus::sleep` says no and the core carries on). Stopped, every clock is off: HCLK reads 0, so SysTick and CYCCNT stand still, and TIM2, the SSIs and UART3 freeze; only the EXTI lines reach the NVIC. The wake takes the MHSI start-up (`STOP_WAKE`, 2 us) and leaves RCC and the oscillators at their reset values, MAINCLK on MHSI, PWR SR1 SPF and CKF set (`Sysctl::stop_exit`). A UART byte is lost if UART3 lacks its clock at any time from its start bit on. Out of a stop the HAL's `rcc::reinit` takes over 2 ms (the HSE's assumed start-up, the PLL lock), so a module frame that wakes the keyboard is lost whole: m6 has the module send it again. A HAL that doesn't restore APB2ENR (seeded) fails 7 of m6's 8 stop tests. Standby isn't modelled.
