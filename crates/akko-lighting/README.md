# akko-lighting

All of the Akko 5075B Plus lighting, as plain logic: no I/O, `no_std`. The firmware calls it once
per frame and sends the colours to the WS2812 chain.

## What it does
- **QMK rgb_matrix, ported bit-exact:**
  - lib8tion maths (`math`) and HSV→RGB (`color`);
  - the task state machine and key hit tracker (`engine`);
  - every effect the board enables (`effects`).
  
  The same inputs give the same colours as QMK's C.
- **The vendor's board code (`board`):**
  - RGB keys and blinks;
  - battery and connection indicators;
  - Caps/Win-lock;
  - the LED test.
- **The side lights (`rgblight`):** the 22 LEDs 84-105, with the board's modes.
- **The settings record (`record`):** the vendor's EEPROM layout, plus our flags.
- **Vial's lighting protocol (`vialrgb`).**

## Board-specific
- `layout` (106 LEDs, 6×15, generated by `tools/gen_leds.py`) is imported statically by the engine.
- The brightness cap and the step sizes are the board's.
- The effect numbering follows the board's `keyboard.json`.

A generic rgb_matrix crate would need the layout as a parameter. That split is planned.

## Tested how
- `python3 -I tools/rgbref/run.py` compiles QMK's real `rgb_matrix.c` for the host and diffs every
  frame (494 cases).
- `tools/rgbref/board.py` does the same for the vendor's board code (27 cases).
- Unit tests: `cargo test -p akko-lighting --target x86_64-unknown-linux-gnu`.
- `sim/tests/m5_lighting.robot` checks what reaches the LEDs.
